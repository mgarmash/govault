# Can GoVault unlock the official Bitwarden browser extension?

**Recommendation, 23 November 2026.** Keep using the official extension for autofill against the same server. A zero-CGO companion is technically plausible on Chromium and Firefox, but the extension hard-codes one native host and offers no desktop provider selection. In 2026.11 the integration can send a vault decryption key in **either direction**. Shipping a drop-in replacement would make installation order part of the vault's trust boundary. Seek an upstream-supported way to select and authenticate a provider before shipping. Safari has a different packaging constraint. [Extension host selection](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/browser/src/platform/ipc/transports/desktop-ipc.transport.ts#L94-L120) · [Released shared-unlock driver](https://github.com/bitwarden/clients/blob/28b247ac34877882aaef4faea082a9f3bb201114/libs/common/src/key-management/shared-unlock/shared-unlock-driver.ts#L49-L76) · [Apple's native messaging model](https://developer.apple.com/documentation/safariservices/messaging-between-the-app-and-javascript-in-a-safari-web-extension)

The manifest maps and legacy implementation links use clients main at `f0be6bb8bd46`. Product documentation describes supported releases, while feature flags in source describe possible execution paths. No browser session or private vault was used. ## Browser registration and the two transport hops

The extension requests native-messaging permission and opens `com.8bit.bitwarden`. The browser resolves that name and starts the registered executable. The official desktop writes the manifests and starts its listener during startup. Registering a host and consenting to synchronized unlock are separate actions. [Browser connection](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/browser/src/platform/ipc/transports/desktop-ipc.transport.ts#L94-L120) · [Desktop startup](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/desktop/src/main.ts#L451-L471) · [Synchronized unlock settings](https://bitwarden.com/help/synchronized-unlock/)

## Protocol generations and trust

**Legacy biometric channel.** The browser generates a temporary 2048-bit RSA key pair. Desktop checks the requested user UUID against its signed-in accounts, creates a fresh AES-256-CBC/HMAC session key and wraps it with RSA-OAEP using SHA-1. Encrypted application messages carry a command, correlation ID, timestamp and operation-specific data. Status returns an enum, presence returns a boolean, and successful account unlock returns the base64-encoded symmetric **user key** inside the protected response. The extension decodes the key and uses it to unlock its local encrypted vault. The master password and OAuth tokens are unnecessary. [Browser setup](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/browser/src/background/nativeMessaging.background.ts#L398-L416) · [Hash selection](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/desktop/src/services/biometric-message-handler.service.ts#L23-L26) · [Account check](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/desktop/src/services/biometric-message-handler.service.ts#L89-L131) · [Command dispatch](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/desktop/src/services/biometric-message-handler.service.ts#L162-L224) · [Desktop key handling](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/desktop/src/services/biometric-message-handler.service.ts#L250-L311) · [Extension consumer](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/browser/src/key-management/biometrics/background-browser-biometrics.service.ts#L149-L175)

An unexpected account, missing session, stale message, cancelled prompt or disconnected proxy can all prevent unlock. The legacy freshness window is ten seconds and pending calls can time out after a minute. Its setup uses an informal correlation-ID marker for newer desktop clients. In desktop 2025.1.4 the optional verification step derived a phrase from the app ID and public key, asked the user to compare it, and remembered confirmation. At the inspected revision setup proceeds directly after the account check and a regression test explicitly expects no fingerprint verification command. A design review must not count that phrase as proof of peer identity. [Error handling](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/desktop/src/services/biometric-message-handler.service.ts#L102-L168) · [Browser timeouts](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/browser/src/background/nativeMessaging.background.ts#L18-L20) · [Marker](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/desktop/src/services/biometric-message-handler.service.ts#L261-L272) · [Historical phrase verification](https://github.com/bitwarden/clients/blob/144f93895758b6c4eb453fe4c7312286a5dd1ee4/apps/desktop/src/services/biometric-message-handler.service.ts#L440-L487) · [Fingerprint regression test](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/desktop/src/services/biometric-message-handler.service.spec.ts#L194-L219) · [Biometrics help](https://bitwarden.com/help/biometrics/)

**SDK IPC.** The non-Safari biometric implementation can select SDK calls by feature flag. The transport wraps a destination, topic and byte array in JSON. It supports forwarded sources, discovers the desktop renderer's application version, waits up to five seconds each for connection and discovery, and retries disconnected transports on a ten-second interval. The discovery result is logged without a minimum-version comparison there. SDK account unlock validates the returned symmetric key for the requested user before unlocking. Readiness, permission and user interaction have distinct failure paths. [Transport and version discovery](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/browser/src/platform/ipc/transports/desktop-ipc.transport.ts#L19-L79) · [Connection lifecycle](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/browser/src/platform/ipc/transports/desktop-ipc.transport.ts#L94-L185) · [Biometric routing and validation](https://github.com/bitwarden/clients/blob/f0be6bb8bd463cdae0cd7afddb2db1cbb694e527/apps/browser/src/key-management/biometrics/background-browser-biometrics.service.ts#L51-L145)

The SDK uses CBOR frames for a two-message Noise NN exchange, encrypted transport and session invalidation. The default suite is P-256, AES-GCM and SHA-256. The source also defines X25519 suites with ChaCha20-Poly1305/BLAKE2s or AES-GCM/SHA-256. NN protects against passive observation. It provides no authenticated peer identity against an active intermediary. A fresh encrypted session alone is insufficient grounds to release a vault key. [SDK protocol and threat model](https://github.com/bitwarden/sdk-internal/blob/5b7fbb413cf0eff108b0abdbc22607945cc36d8b/crates/bitwarden-ipc/src/crypto_provider/noise/mod.rs#L1-L55) · [Suites](https://github.com/bitwarden/sdk-internal/blob/5b7fbb413cf0eff108b0abdbc22607945cc36d8b/crates/bitwarden-ipc/src/crypto_provider/noise/handshake.rs#L20-L55)

**Synchronized unlock.** Both directions use an account-specific state message with a transition time. Unlocked state carries the actual symmetric key. Newer state wins and an equal timestamp resolves toward locked. The SDK checks the permitted peer and local account, checks web origin against vault URL when applicable, and can temporarily suppress a peer's vault timeout. A provider therefore has to preserve manual locks, ordering, timeout policy and account isolation even across sleep, browser restarts and dropped connections. An implementation that only answers biometric unlock requests covers a narrower feature. [Message and ordering](https://github.com/bitwarden/sdk-internal/blob/5b7fbb413cf0eff108b0abdbc22607945cc36d8b/crates/bitwarden-shared-unlock/src/message.rs#L9-L89) · [Peer checks](https://github.com/bitwarden/sdk-internal/blob/5b7fbb413cf0eff108b0abdbc22607945cc36d8b/crates/bitwarden-shared-unlock/src/peer.rs#L194-L256) · [Local lock and unlock](https://github.com/bitwarden/clients/blob/28b247ac34877882aaef4faea082a9f3bb201114/libs/common/src/key-management/shared-unlock/shared-unlock-driver.ts#L49-L97)

## GoVault feasibility

| Platform | Assessment |
| --- | --- |
| macOS, Chromium or Firefox | Most promising for GoVault. Its Keychain adapter already distinguishes hardware-enforced biometric access from the Developer ID release's application-gated fallback. An external request adds another route to the key. Require an account-bound decision and fresh local authorization for biometric release even if the GoVault window is already unlocked. Keep this distinct from explicit consent to bidirectional synchronization. ## Prior art and first scope

Goldwarden advertises Linux browser biometrics and reports that development is paused. Its author's smaller bw-bio-handler implements a biometric subset with polkit. The Windows project bwbio reports Windows Hello and TPM-backed protection and describes itself as unaudited. These projects establish historical feasibility. Their cited documentation provides no evidence of compatibility with the 2026.11 synchronized-unlock protocol. [Goldwarden](https://github.com/quexten/goldwarden/blob/7727d3ac291d6f38473d8861a187c56efb449acb/Readme.md#L1-L18) · [bw-bio-handler](https://github.com/quexten/bw-bio-handler/blob/ebbfc2d00bd1341366c9b287940ddfcd718e2e8e/Readme.md#L3-L21) · [bwbio](https://github.com/Aalivexy/bwbio/blob/808f8b38eda5a5c412c690f26d9c434ed961abfc/README.md#L3-L26)

**First scope and estimate.** Allow roughly 2–4 engineer-days for a macOS feasibility study under a GoVault-owned host name with a development extension and synthetic account data. Verify signed companion packaging, status/discovery, origin and peer checks, Touch ID cancellation, and lock during a pending prompt. That measures packaging and trust mechanics only. For an upstream-approved macOS provider, budget several engineer-weeks for implementation, failure tests and compatibility QA, contingent on a supported selection mechanism. A three-platform production estimate needs answers on Windows protected key use, Linux distribution support, and the release/feature-flag matrix for self-hosted Vaultwarden. The first decision is whether upstream will expose a stable provider identity and a user-visible choice for both directions of key transfer.
